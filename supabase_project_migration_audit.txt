FAIL F1 — The Phase 6 gate cannot execute on Supabase: cron.job is SELECT-only
          [REPO] + [PLATFORM] + [LOCAL DEMO]                    Severity: blocker

  The canonical gate is a direct UPDATE:
    supabase/migrations/20261016090100_phase6_autonomy_crons.sql:189
    supabase/migrations/20261016090200_phase6_activation_gate.sql:27
    src/test/harness/cron-contract.ts:148 (GATE_SQL, RESUME_ALL_SQL:157)
    phase6_activation_checklist.txt:135, 493, 514, 530, 556-566
    docs/OPERATIONS.md:197, 204, 207, 236, 283-294

  On Supabase the `postgres` role is not a superuser (initdb's superuser is
  `supabase_admin`: supabase/postgres Dockerfile-17:176 POSTGRES_USER, and only
  supabase_admin is altered to superuser in init-scripts/…0000-initial-schema.sql:8).
  [PLATFORM] The image also enforces SELECT-only access for `postgres` on cron.job:
    migrations/db/migrations/20231020085357_revoke_writes_on_cron_job_from_postgres.sql
      revoke all on table cron.job from postgres;
      grant select on table cron.job to postgres with grant option;
    and extensions.grant_pg_cron_access() (re)applies exactly that on
    CREATE EXTENSION (ansible/…/pg_cron/after-create.sql, same two lines).

  [LOCAL DEMO] A role holding only SELECT on cron.job gets:
    update cron.job set active = false … → "permission denied for table job"
    select count(*) from cron.job        → 14 (works)
  So `db push` on the new project would fail at the LAST section of the cron
  migration (3b), aborting the push; the repair migration 20261016090200 would
  never run, and every activation step (G1-G3) would fail the same way.
  The earlier "PASS — SQL form verified offline" was true only in a harness
  where postgres owns cron.job.

  RECOMMENDED FIX (to be implemented, not now):
    select cron.alter_job(jobid, active := false)
      from cron.job
     where jobname in ('write-desk','publish-scheduler',
                       'auto-publish-morning','auto-publish-midday','auto-publish-every',
                       … the same 8 names …);
    -- "resume everything":  select cron.alter_job(jobid, active := true) from cron.job;
    -- "stop everything":    select cron.alter_job(jobid, active := false) from cron.job;

  Why this is the right primitive:
    [PLATFORM] pg_cron 1.6.4 src/job_metadata.c, AlterJob():
      - builds SET only from non-NULL arguments, so `active` alone never
        touches schedule/command/database;
      - runs the UPDATE as the extension owner (SetUserIdAndSecContext(
        CronExtensionOwner(), …)), so the caller needs EXECUTE, not UPDATE;
      - adds `and username = currentuser` for non-superusers — the jobs are
        created by `postgres` (ScheduleCronJob uses the current user as the
        job username), so `postgres` owns them;
      - calls InvalidateJobCache(), which is the same no-restart guarantee the
        UPDATE had.
    [PLATFORM] Supabase grants `all on all functions in schema cron to postgres
      with grant option`, so EXECUTE survives pg_cron's own REVOKE … FROM PUBLIC.

  Test-harness implications (part of the fix):
    - cron-contract.ts, both migrations, the checklist, OPERATIONS and the
      tests must change in one commit; the contract file already centralises
      the statement, which makes this one edit plus docs.
    - sql-staging.ts must model the platform: revoke INSERT/UPDATE/DELETE on
      cron.job from postgres (keep SELECT) and make the cron.alter_job stub
      SECURITY DEFINER with an owner switch, mirroring AlterJob(). Without
      this the regression test would be green on a broken design again.

FAIL F2 — anon/authenticated can execute every SECURITY DEFINER function the
          Phase 6 migrations create (including the publishing triggers)
          [REPO] + [PLATFORM] + [LOCAL DEMO]                 Severity: critical

  Every function is revoked from the PUBLIC pseudo-role only:
    20261016090000_phase6_autonomy_schema.sql:263,294,316,330,386,409
      record_alert, claim_ingested_items, category_published_count,
      newsroom_llm_calls_today, newsroom_status, prune_automation_tables
    20261016090100_phase6_autonomy_crons.sql:87
      newsroom_trigger (builds net.http_post with the Vault secret)
    20261015120200_reschedule_auto_publish_18_per_day.sql:85,128,166
      trigger_auto_publish, trigger_breaking_news_monitor,
      trigger_notifications_dispatcher
    Pattern used everywhere: `revoke all on function … from public;`

  [PLATFORM] Supabase grants privileges at creation time:
    init-scripts/00000000000000-initial-schema.sql:41
      alter default privileges in schema public grant all on functions
        to postgres, anon, authenticated, service_role;
    Those are explicit per-role grants. `REVOKE … FROM public` removes only the
    PUBLIC entry and leaves anon/authenticated/service_role intact.

  [LOCAL DEMO] Replayed the full 13-migration chain on PostgreSQL 18.6 with
    those three default-privilege lines applied first:
      has_function_privilege('anon', …, 'EXECUTE') = TRUE for
        newsroom_trigger, trigger_auto_publish, trigger_breaking_news_monitor,
        trigger_notifications_dispatcher, prune_automation_tables,
        claim_ingested_items, record_alert, newsroom_status
      Tables stayed locked (anon SELECT/INSERT false on content_sources,
      ingested_items, pipeline_runs; posts SELECT true, INSERT false).
    Without those default-privilege lines the current test passes — which is
    exactly why the suite is green: sql-staging.ts:28-32 creates the roles but
    not the grants. phase6-sql.test.ts:246-279 asserts a property the platform
    does not provide.

  Why it matters on a public news site (the publishable/anon key is shipped in
  the JS bundle by design):
    - trigger_auto_publish('morning') / newsroom_trigger('auto-publish') →
      a full edition run with the Vault secret attached: publishing plus LLM
      spend, triggered by any visitor.
    - prune_automation_tables() → deletes retention rows.
    - claim_ingested_items() / record_alert() → queue disruption, alert spam.
  PostgREST exposes every public function the caller may execute, so these are
  reachable as POST /rest/v1/rpc/<name>.

  FIX (to be implemented):
    - new migration: for each function,
        revoke all on function … from public, anon, authenticated;
        grant execute on function … to service_role;
      (keep the existing PUBLIC revoke; service_role is required for the
      edge functions, and currently only has it via default privileges).
    - sql-staging.ts: apply Supabase's default privileges in the prelude so the
      harness matches the platform.
    - phase6-sql.test.ts: keep the assertion, now meaningful; add a case that
      fails if a future function forgets the explicit revoke.
  [LIVE] Confirmation query (run before/after; expected: every row FALSE and
  no `anon=` / `authenticated=` entry):
    select p.proname, p.proacl
      from pg_proc p join pg_namespace n on n.oid = p.pronamespace
     where n.nspname = 'public' and p.prosecdef
     order by 1;

  wrapper: apps/cli-go/pkg/migration/apply.go:62-75 loops per file and calls

  true. Recommendation: keep the historical migrations as records (repo
  policy: applied migrations are history) and document this window; a squash
