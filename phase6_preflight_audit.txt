WHAT WAS VERIFIED FROM UPSTREAM SOURCE (label: UPSTREAM — not the target)
--------------------------------------------------------------------------------
U1. pg_cron v1.6.4 defines
      cron.alter_job(job_id bigint, schedule text, command text, database text,
                     username text, active boolean) RETURNS void
    in pg_cron--1.3--1.4.sql (i.e. available since 1.4). The C implementation
    (src/job_metadata.c AlterJob) builds the UPDATE from the non-NULL arguments
    only, runs with the extension owner's privileges, and invalidates the job
    cache. The script ends with
      REVOKE ALL ON FUNCTION cron.alter_job(...) FROM public;
    and the same for cron.schedule_in_database(...).
    Source: codeload.github.com/citusdata/pg_cron, tag v1.6.4.

U2. supabase/postgres builds pg_cron 1.6.4 for PostgreSQL 15, 17 and
    orioledb-17 (nix/ext/versions.json). The current image tag referenced by the
    CLI issue below is postgres:17.11.0.002-r0 — the same PostgreSQL 17.11
    recorded for the target in the earlier audit. A fresh PG 17 project that
    creates pg_cron gets 1.6.4.

U3. The grants that make cron usable for `postgres` come from the image's
    after-create script (ansible/files/postgresql_extension_custom_scripts/
    pg_cron/after-create.sql):
      grant usage on schema cron to postgres with grant option;
      grant all on all functions in schema cron to postgres with grant option;
      alter default privileges ... grant all on functions to postgres ...
    and from the platform migration 20220713082019 (applied to hosted
    projects), which does the same for existing and future functions.
    The current event trigger extensions.grant_pg_cron_access() does NOT grant
    EXECUTE on already-created functions: it sets default privileges and grants
    ALL on the cron TABLES only.

U4. On hosted projects the after-create script runs, so `postgres` holds
    EXECUTE on cron.alter_job. On the CLI's Docker runtime it does not:
    supabase/cli issue #6978 (opened 2026-10-03) reports
      Docker: {supabase_admin=X/supabase_admin}
      Native: {supabase_admin=X/supabase_admin,postgres=X*/supabase_admin}
    and the exact symptom "permission denied for function alter_job".
    This is the failure mode to rule out on the target.

U5. supabase/postgres migration 20231020085357 leaves `postgres` with SELECT
    only on cron.job — which is why the gate uses cron.alter_job (F1).

U6. supabase/postgres migration 20221207154255 grants `postgres` and
    `service_role` access to vault.secrets / vault.decrypted_secrets and the
    vault RPCs; 20220713082019 grants EXECUTE on net.http_post to postgres (and
    to the API roles). These are the run-time dependencies of newsroom_trigger.

CHECK 1 — pg_cron version and alter_job support
--------------------------------------------------------------------------------
Verdict: BLOCKED

Needed: the installed extversion on the target, because the chain calls
  cron.schedule_in_database(..., active := false)   (first cron file)
  cron.alter_job(jobid, active => false)            (gate + repair)
Both functions first appear in pg_cron 1.4 (U1). An older installed version
makes the first cron migration fail at `schedule_in_database`, before the gate
and the repair run — the repair cannot rescue it.

Query: phase6_preflight_readonly.sql section C and D.
Expected (repository assumption, NOT verified):
  pg_cron 1.6.x, owner supabase_admin, both functions present.
FAIL if extversion < 1.4 or either function is absent.
Note: if pg_cron is not installed at all, migration 20260503120214 creates it
(assuming the execution role is allowed to — see Check 3), and the version
would then be the image default (1.6.4).

CHECK 2 — can the migration role call cron.alter_job?
--------------------------------------------------------------------------------
Verdict: BLOCKED

Query: phase6_preflight_readonly.sql section D and E.
Expected (repository assumption): the ACL contains
  {supabase_admin=X/supabase_admin, postgres=X*/supabase_admin}
so `has_function_privilege('postgres', ..., 'EXECUTE')` is true.

This is the highest-risk assumption in the chain. pg_cron revokes both
alter_job and schedule_in_database from PUBLIC (U1); nothing in the extension
grants them back. The grant comes from Supabase's after-create script (U3) and
is demonstrably absent on one supported runtime (U4). If it is missing on the
target, `db push` aborts with "permission denied for function ..." — at
20261015120200 (schedule_in_database) or at 20261016090100 section 3b (the
gate, alter_job) — and the push stops mid-chain.

Mitigation if false (requires separate approval, not performed here):
  - enable/manage pg_cron through the dashboard so the after-create script
    runs, or
  - have the platform owner grant EXECUTE explicitly, or
  - run the push as a role that owns the extension.

Target facts still unknown (blocked):

    .schema_migrations (0 = fresh, 14 = already pushed, anything between =

Ordering risks that do not depend on the target:
  R-A. `db push` applies one file per transaction; a failure mid-chain leaves
       the earlier files applied. Since every file is recorded individually,
       re-running the push resumes at the failed file. The gate and the
       privilege repair are both re-runnable.
  R-B. Two historical files are not idempotent if executed twice by hand:
       20260507084537 (`ALTER PUBLICATION supabase_realtime ADD TABLE
       notifications` errors if the table is already a member) and
       20260503120214 (creates policies without IF NOT EXISTS). The CLI does
       not re-run applied files, so this only bites on manual re-execution.
  R-C. The repository now edits migration files that were already committed
       (1da5872 adds the per-file privilege blocks). On a project that had
       already recorded those versions, the edits do not re-run; the repair
       migration 20261017090000 carries the same end state. This is safe but
       means "what is in the repo" and "what that project applied" differ —
       relevant only if the target is such a project.

CHECK 7 — blockers, risks, discrepancies between repo assumptions and live DB
--------------------------------------------------------------------------------
Verdict: PASS (analysis complete; the blockers themselves are listed below)

Repository assumptions that the live database may contradict:

  A1  "postgres can execute cron.alter_job and cron.schedule_in_database."
      Evidence gap: the grant is an image/platform behaviour, not a pg_cron
      guarantee (U1, U3). Observed missing on at least one runtime (U4).
      Severity: blocks the push at 20261015120200 (schedule_in_database) or
      20261016090100 3b (alter_job).
      Detect: check 2 query. Do not start the push before it returns true.

  A2  "pg_cron is 1.4+."
      Missing on old projects; breaks the first cron migration.
      Severity: blocks the push at 20261016090100 / 20260503120747.
      Detect: check 1 query.

  A3  "pg_net exposes net.http_post(url, body, params, headers,
      timeout_milliseconds)."
      Named-argument resolution happens at run time, so an older pg_net fails
      when the trigger runs, not at push time.
      Severity: runtime failure of every scheduled job.
      Detect: section F (`to_regprocedure`).

  A4  "The project is empty / fresh."
      If it already has tables or jobs from manual work, several migrations
      fail on duplicate objects or leave drift.
      Detect: sections I and J.

  A5  "The target was never pushed."
      If it was, the checked-in edits do not apply retroactively; the repair
      migration is the backstop for privileges, and the F4 "born inactive"
      change does not retroactively alter existing job rows (the gate still
      forces them inactive at 090200/17090000).
      Detect: section J.

  A6  "Vault rows exist before activation."
      Not needed for the push, needed before any gated job is enabled; the
      trigger fails closed without them (by design, F3).
      Detect: read vault.decrypted_secrets names only — never the values.

Non-blocking discrepancies found during this audit:
  - supabase/config.toml and .env still point at the old project
    (ruusbjlabbojpbawbphc); the target is xuqxautmflofkvbsaanh. That is the
    documented cutover step, not a migration prerequisite.
  - README/OPERATIONS describe `newsroom_base_url` as mandatory; that matches
    the code (commit 1da5872), no drift.
  - The repository's local harness grants EXECUTE on cron.alter_job to postgres
    explicitly. That models the hosted behaviour (U3/U4), not every runtime;
    a harness cannot detect A1 on the target.

Security note (read-only observation): pg_cron itself grants SELECT on
cron.job to PUBLIC (pg_cron.sql). On Supabase that is not reachable through
PostgREST because the cron schema is not exposed, and 20231020085357 keeps
`postgres` at SELECT only on that table. No action is recommended here.

RECOMMENDED NEXT STEP
--------------------------------------------------------------------------------
Do not run `supabase db push` yet. One query decides it:

  select has_function_privilege('postgres',
           'cron.alter_job(bigint,text,text,text,text,boolean)', 'EXECUTE') as can_alter,
         has_function_privilege('postgres',
           'cron.schedule_in_database(text,text,text,text,text,boolean)', 'EXECUTE') as can_schedule,
         (select extversion from pg_extension where extname = 'pg_cron') as pg_cron_version
 where to_regprocedure('cron.alter_job(bigint,text,text,text,text,boolean)') is not null;

  (a project without pg_cron returns zero rows: extension not installed).
  - both true and version >= 1.4  -> the two hard blockers are gone; proceed to
    a controlled dry run of the remaining checks (3-6) and then a push window
    with the gate verified afterwards (8 inactive / 6 active).
  - either false                  -> stop. Fix the grant first (dashboard
    enable, or explicit grant by the platform owner); the push will abort.
  - version < 1.4                 -> stop. The chain cannot be applied; the
    repository's documented floor is 1.4.

After the push, the same pack verifies the result: section G must show
8 inactive / 6 active, section H must show no public access beyond the view
counter, and section J must list all 14 versions.
