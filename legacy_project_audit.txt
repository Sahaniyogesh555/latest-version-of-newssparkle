4.4 Grant path for cron functions                     RISK — NOT VERIFIABLE
    Event triggers present and enabled ('O'):
      issue_pg_cron_access  -> extensions.grant_pg_cron_access()
      issue_pg_net_access   -> extensions.grant_pg_net_access()
    Both owned by supabase_admin, on ddl_command_end.

    The DEPLOYED definition of grant_pg_cron_access() was read on the target
    (pg_get_functiondef). It does, in this order:
      grant usage on schema cron to postgres with grant option;
      alter default privileges in schema cron grant all on tables/functions/
        sequences to postgres with grant option;
      alter default privileges for user supabase_admin in schema cron ... ;
      grant all privileges on all TABLES in schema cron to postgres;
      revoke all on table cron.job from postgres;
      grant select on table cron.job to postgres with grant option;
      revoke trigger on cron.job_run_details from postgres;

    It does NOT contain `grant all on all functions in schema cron to postgres`.
    The ALTER DEFAULT PRIVILEGES lines only affect functions created LATER;
    alter_job and schedule_in_database are created during the same CREATE
    EXTENSION, before the trigger runs. Both are explicitly REVOKEd from PUBLIC
    by pg_cron itself.

    Therefore EXECUTE for `postgres` on cron.alter_job / cron.schedule_in_database
    must come from the supautils after-create hook:
      /etc/postgresql-custom/extension-custom-scripts/pg_cron/after-create.sql
    which contains exactly
      grant usage on schema cron to postgres with grant option;
      grant all on all functions in schema cron to postgres with grant option;

    Supporting evidence that this hook works on this project:
      * supautils.extension_custom_scripts_path =
        supautils.privileged_extensions_custom_scripts_path =
        /etc/postgresql-custom/extension-custom-scripts
      * that is the path supabase/postgres Dockerfile-17 line 135 copies the
        scripts into
      * the project is Supabase Cloud (api.supabase.com, ap-south-1), not the
        CLI Docker runtime that supabase/cli#6978 reports as broken
      * INDIRECT PROOF the hook runs here: postgres currently holds
        SELECT on vault.decrypted_secrets and vault.secrets, and EXECUTE on
        vault.create_secret(text,text,text,uuid) — exactly the grants that
        supabase_vault/after-create.sql makes, and which nothing else grants.
