F1 — THE GATE USED AN API THE PLATFORM FORBIDS
----------------------------------------------
Root cause: Supabase grants the `postgres` role SELECT only on cron.job
(supabase/postgres 20231020085357 + the grant_pg_cron_access() event trigger),
so `update cron.job set active = ...` fails with "permission denied for table
job" — inside `db push` it would abort the migration at the gate and every
activation step after it.

Change: the canonical gate is now
  select cron.alter_job(jobid, active => false)
    from cron.job
   where jobname in ('write-desk','publish-scheduler', …the same 8…);
with the resume form `select cron.alter_job(jobid, active => true) from
cron.job` and the same for "stop everything". It appears verbatim in
20261016090100 §3b, 20261016090200, 20261017090000, the checklist (B2, G1-G3,
section H) and docs/OPERATIONS.md — five copies, asserted identical.

Why it is correct, from pg_cron 1.6.4 itself:
  - cron.alter_job(job_id bigint, schedule text default null, command text
    default null, database text default null, username text default null,
    active boolean default null) returns void — pg_cron--1.3--1.4.sql, so the
    function has existed since 1.4 and the signature above is the real one.
  - AlterJob() builds a SET list only from the non-NULL arguments, so
    `active => false` cannot touch schedule/command/database.
  - it runs the UPDATE as the extension owner (SetUserIdAndSecContext), so
    EXECUTE is sufficient; no table privilege is needed.
  - for a non-superuser it filters `username = currentuser`; the jobs are
    created by `postgres` (ScheduleCronJob takes the current user), and the
    operator runs the SQL as `postgres`, so ownership holds.
  - it calls InvalidateJobCache(), the same cache refresh the UPDATE relied on.

Regression tests (src/test/phase6-sql.test.ts):
  - "uses the gate API the platform actually permits, not a direct UPDATE":
    a SELECT-only role is denied `update cron.job`; alter_job is SECURITY
    DEFINER and executable by postgres; no migration may contain the UPDATE.
  - "the gate changes only `active`, never a schedule or a command".
  - "runs the gate on a project that has no jobs yet without failing".
  - repo-integrity: "embeds the identical gate statement in every migration
    and both operator documents" (5 files) and "never issues the UPDATE form
    the platform rejects" (real statements only, prose is allowed).

F2 — PUBLIC ROLES COULD EXECUTE THE PRIVILEGED FUNCTIONS
--------------------------------------------------------
Root cause: the migrations only did `revoke ... from public`, but Supabase
grants EXECUTE to anon/authenticated/service_role at creation time
(init-scripts/00000000000000-initial-schema.sql:41). The per-role grants
survived, so the publishing triggers — and newsroom_trigger, which attaches the
Vault secret — were callable with the public anon key.

Change (new migration 20261017090000_phase6_privileges_and_gate_repair.sql):
every public function is now revoked from public, anon, authenticated AND
service_role by name, then granted only where it is genuinely needed:
  anon, authenticated          increment_post_views (the view counter)
  service_role                 record_alert, claim_ingested_items,
                               category_published_count, newsroom_llm_calls_today,
                               newsroom_status, prune_automation_tables,
                               prune_post_view_events
  postgres (pg_cron)           newsroom_trigger, trigger_auto_publish,
                               trigger_breaking_news_monitor,
                               trigger_notifications_dispatcher, the prunes
  nobody                       touch_updated_at (trigger helper)
service_role deliberately does NOT get the HTTP triggers: an edge function has
no reason to make the database send a request carrying the automation secret.

The harness now models the platform: SUPABASE_PRELUDE applies Supabase's four
default-privilege statements, so the old design fails here (it did: the new
tests were red until the migration was added) and any future function that
forgets its revoke fails too.

Regression tests:
  - "locks down the RPCs …" (11 signatures, anon+authenticated denied);
  - "grants each privileged function only to the role that calls it";
  - "has no SECURITY DEFINER function reachable by the public roles except the
    view counter" (whole-catalog sweep).

PHASE 6.1 CORRECTION - FAIL-CLOSED CRON GATE (targeted safety fix)
====================================================================
Date: 2026-10-15 | Branch: arena/e59698ee-latest-version-of-newssparkle
Audited commit: 9cd5cc0. Base commit for this correction: 9cd5cc0.
Scope: the four defects found while auditing the activation procedure, and

WHAT WAS WRONG AT 9cd5cc0
-------------------------
1. RACE: the cron migration created all 14 jobs ACTIVE, so `supabase db push`
   started publishing immediately. The documented safety barrier was a manual
   pause AFTER the push - a window in which publish-scheduler (*/10) or
   auto-publish-midday could publish, and newsroom-maintenance (40 * * * *)
   could archive, before any operator looked. A pause that must win a race is
   not a safety barrier.
2. MISMATCH: the checklist paused seven jobs (including
   notifications-dispatcher), the test suite tested six, and docs/OPERATIONS.md
   still listed the old Phase 5 set of five. Three different "safe job sets".
3. ORDERING: newsroom-maintenance was paused only as a side effect of a
   blanket update and had no separate approval step, yet it is the one job that
   changes pages readers can already see (archives >730-day, <50-view posts).
4. COVERAGE: no test asserted that the jobs are inactive immediately after a
   fresh migration, or after a migration re-run.

THE FIX (smallest fail-closed design: the row is born inactive)
--------------------------------------------------------------
The eight jobs that can publish, spend LLM budget, alert readers or archive
published content are now created INACTIVE by the migration itself:

  select cron.schedule_in_database('<name>', '<schedule>',
         $$ <same command as before> $$, current_database(), active := false);

cron.schedule_in_database(name, schedule, command, database, username default
null, active default 'true') exists from pg_cron 1.4 and is the ONLY SQL entry
point that can create an inactive job: cron.schedule's three-argument form
passes NULL `active`, which pg_cron reads as true (verified in the pg_cron
sources, cron_schedule_named -> ScheduleCronJob, v1.4.0 ... v1.6.4).
The six safe jobs (ingestion, trends, monitor, feed validation, both prunes)
keep cron.schedule, so monitoring and ingestion are not silently disabled.

Gated  = created INACTIVE (8): write-desk, publish-scheduler,
         auto-publish-morning, auto-publish-midday, auto-publish-evening,
         breaking-news-monitor, notifications-dispatcher, newsroom-maintenance
Safe   = created ACTIVE   (6): ingest-feeds, trend-watch, phase6-monitor,
         validate-feeds-daily, prune-post-view-events, prune-automation
All 14 schedules and commands are unchanged.

FRESH INSTALL vs RE-RUN (the two behaviours the audit asked for)
---------------------------------------------------------------
FRESH INSTALL (`db push` on a project that never ran Phase 6): no window. The
  gated rows are inserted inactive in the same statement that creates them, so
  no publishing-capable job and no maintenance job can tick before preflight.
  Only ingestion, trends, the monitor and the prunes run: they add candidates
  and alerts and delete nothing published. Verified on the migration text and
  by executing it in the staging harness (tests below).
MIGRATION RE-RUN / db reset on an ALREADY-ACTIVATED project: safe and
  repeatable. The recreate path unschedules the 14 names first, then
  re-creates them; the upsert is
  `on conflict on constraint jobname_username_uniq do update set schedule,
  command, database` - it never touches `active` - and the gate
  `update ... set active = false` runs again at the end. Net effect: back to
  8 inactive / 6 active. Verified: the suite enables every job, re-applies the
  migration, and asserts 8/6 again.
OPERATOR ACTIVATION (the only way jobs switch on): three documented steps, in
  order, in the checklist. G1 write-desk + publish-scheduler; G2 (after 24h)
  the three editions + breaking-news-monitor + notifications-dispatcher; G3
  newsroom-maintenance ONLY after the B3 archive pre-check has been read and
  approved. G3 is deliberately separate: an operator who has not reviewed the
  730-day/50-view rows never has to authorise archiving, and leaving the job
  inactive breaks nothing else. The test reads these exact statements out of
  the checklist file and runs them, so the doc and the tested behaviour cannot
  drift apart.

Phase 0 privilege/gate repair; the original 6.1 audit ran against 12). Verified

One file is deliberately NOT in the commit: .github/workflows/ci.yml. The GitHub
App installation used to push this repository does not hold the `workflows`
permission, and GitHub rejects any push whose commits create, edit or delete a
file under .github/workflows ("refusing to allow a GitHub App to create or
update workflow ... without `workflows` permission"). Pushing the workflow file
and pushing the code cannot happen in the same commit - GitHub rejects the
whole ref update.

Resolution: the workflow definition is preserved in the repository as
docs/ci-workflow.pending.yml, with instructions in its header and in README.md.
It needs one commit by a token that holds the `workflows` scope (the GitHub web
UI or a reconnect with that permission works). Until then `npm run verify` is
the same gate, run locally, and it passes.

The pre-existing .github/workflows/npm-publish-github-packages.yml is left
untouched for the same reason.
