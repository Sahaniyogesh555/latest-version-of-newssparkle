4. BUGS FOUND AND FIXED IN 6.1
------------------------------
FIXED  breaking-news-monitor was dead in production, silently (highest impact
       find). It parsed feeds with `new DOMParser()`, but Deno does not define
       DOMParser (`typeof DOMParser` = "undefined" on deno 2.9.6, verified on
       the real runtime). Every run threw a ReferenceError that the surrounding
       try/catch swallowed, so the monitor reported "No new breaking item
       found" forever while thinking all three feeds were empty. Repointed to
       the shared regex-based parseFeedXml() that ingest-feeds uses and that is
       already tested for RSS, Atom and garbage input. New guard:
       repo-integrity fails if any edge function references a browser-only
       global. This survived CI because CI never ran Deno.
FIXED  Undocumented secrets the code reads: CRON_SECRET, AUTO_PUBLISH_URL
       (both used by breaking-news-monitor) - now in .env.example, together
       with the second Vault name newsroom_base_url (was in neither doc).
FIXED  .env.example advertised GNEWS/NEWSAPI/SERPAPI keys as optional sources
       although Phase 6 reads sources from content_sources; relabelled legacy
       so an operator does not configure and pay for dead keys.
FIXED  Removed SIMHASH_PREFILTER_BITS, a constant that implied a database
       prefilter nobody implemented (the archive comparison runs the exact
       4-shingle Jaccard over the last 7 days / 80 posts).
FIXED  docs/OPERATIONS.md said "deploys all seven" (there are 13) and its pause
       recipe covered only the 5 Phase 5 jobs.
NEW    Safe first-activation procedure (pause/publish/resume, ordered smoke
       test, stop conditions) in OPERATIONS.md.

5. COST AND RESOURCE ESTIMATE (after activation)
------------------------------------------------
Invocations ~542/day (ingest 72, publish-scheduler 144, write-desk 48,
breaking-news 48, notifications 144, monitor 48, maintenance 24, trends 8,
editions 3, validate 1, prunes 2) = ~16k/month.
Feeds: 72 runs x 24 sources = 1728 GETs/day at 40-80 KB, nothing stored beyond
       candidates that pass validation.
LLM: 2-4 calls per published story; the cap is 18 stories/day, so ~36-72
     calls/day typical against a hard 220/day budget the desk checks first.
     At gpt-4o-mini rates that is roughly $0.30-0.60/day worst case.
Images: <=36 provider calls/day (Unsplash/Pexels free tiers allow 50/hour);
        picsum fallback is free.
Database: ~150-400 new candidates/day, ~542 run rows/day, ~24 health checks/day
          - steady state tens of MB, inside current Supabase tiers.
Headroom: publishing is capped at 18/day while the queue fills with hundreds of
          candidates, so the system idles cheaply instead of overspending.

6. SAFE ACTIVATION (order matters)
----------------------------------
The migration creates the cron jobs ACTIVE, so `supabase db push` starts the
loop. Instead:
 1. db push, then immediately pause the writing/publishing jobs:
      select cron.alter_job(jobid, active := false) from cron.job
       where jobname in ('write-desk','publish-scheduler',
             'auto-publish-morning','auto-publish-midday','auto-publish-evening',
             'breaking-news-monitor','notifications-dispatcher');
    (ingest + phase6-monitor stay on so candidates and alerts are visible)
 2. Set the secrets (Vault + function env, identical value).
 3. Deploy functions; confirm an unauthenticated POST returns 401.
 4. Manual dry run, one stage at a time (section 2) - do not enable publishing
    before this passes.
 5. Re-enable write-desk + publish-scheduler, watch 24h, then re-enable the
    editions and breaking-news-monitor.
Stop conditions: monitor ok:false, nothing written in 12h, or any post that
reads wrong -> pause with the block above, fix, repeat steps 4-5.

7. EMERGENCY STOP
-----------------
  select cron.alter_job(jobid, active := false) from cron.job where jobname in
    ('write-desk','publish-scheduler','auto-publish-morning','auto-publish-midday',
     'auto-publish-evening','breaking-news-monitor');   -- stop publishing
  update cron.job set active = false;                    -- stop everything
  update public.content_sources set active = false;      -- stop one/all feeds
Nothing is deleted: scheduled posts stay scheduled and resume when the jobs are
re-enabled.

11. REMAINING RISKS
-------------------
- The first live ingest run is the first time the 24 seeded feeds are fetched
  from Supabase's network; expect a few to need replacing.
- Model quality is the largest uncontrollable variable; the review lane (55-74)
  is the mitigation and needs a human to stay one.
- The legacy anon JWT in the first migration is still in git history: rotate it
  (OPERATIONS.md section 2).
- auto_publish_secret must match between Vault and the function environment; a
  mismatch fails closed (401) but publishes nothing.

12. REPOSITORY STATE
--------------------
Everything above is committed and pushed to
arena/e59698ee-latest-version-of-newssparkle.

One file is deliberately NOT in the commit: .github/workflows/ci.yml. The GitHub
App installation used to push this repository does not hold the `workflows`
permission, and GitHub rejects any push whose commits create, edit or delete a
file under .github/workflows ("refusing to allow a GitHub App to create or
update workflow ... without `workflows` permission"). Pushing the workflow file
and pushing the code cannot happen in the same commit - GitHub rejects the
whole ref update.

Resolution: the workflow definition is preserved in the repository as
docs/ci-workflow.pending.yml, with instructions in its header and in README.md.
It needs one commit by a token that holds the `workflows` scope (the GitHub web
UI or a reconnect with that permission works). Until then `npm run verify` is
the same gate, run locally, and it passes.

The pre-existing .github/workflows/npm-publish-github-packages.yml is left
untouched for the same reason.
