    THE FOUR CLASSES OF JOB, AND WHY EACH IS WHERE IT IS
    (a) publishing-capable — can end with a live article (5, all inactive):
           publish-scheduler: the only code that sets status='published'
             (pipeline.ts runPublishScheduler). Cron `*/10 * * * *`.
           auto-publish-morning/midday/evening: step 3 of `auto-publish` calls
             the same runPublishScheduler, so an edition run publishes real
             articles. Cron `0 6|12|18 * * *`.
           breaking-news-monitor: its whole job is to call auto-publish. `*/30`.
    (b) content generation — cannot publish, but spends LLM budget and queues
        posts a later run releases (1, inactive):
           write-desk: writes status scheduled/review/rejected only, always with
             published_at null, but a queued story goes live as soon as the
             scheduler runs. Cron `*/30 * * * *`.
    (c) reader-alert — publishes nothing, but writes reader-facing
        notifications about a published post (1, inactive):
           notifications-dispatcher: gated so a test article cannot ping
             readers. Cron `*/10 * * * *`.
    (d) destructive maintenance — mutates published content (1, inactive):
           newsroom-maintenance: repairs broken featured images and archives
             published posts older than 730 days with fewer than 50 views.
             Gated until step B3 and G3 are done. Cron `40 * * * *`.
    (e) safe-operational — neither publishes nor touches published content
        (6, active): ingest-feeds (candidates only), trend-watch,
        phase6-monitor (reads + writes alerts), validate-feeds-daily,
        prune-post-view-events, prune-automation.

    WHY cron.alter_job, NOT `update cron.job`
           Supabase gives the `postgres` role SELECT only on cron.job
           (supabase/postgres migration 20231020085357, re-applied whenever
           pg_cron is created). A direct UPDATE therefore fails with
           "permission denied for table job" — in the SQL editor and inside
           `db push` alike. It is not a role problem and retrying will not help.
           cron.alter_job(job_id, schedule, command, database, username, active)
           is the supported API from pg_cron 1.4: it runs as the extension
           owner, changes only the arguments supplied (so schedules and
           commands survive untouched), invalidates the job cache the same way
           the UPDATE did, and is granted to `postgres` by Supabase. The
           parameter is named `active`: a wrong name fails with
           "function cron.alter_job(bigint, active => boolean) does not exist".
           It also only touches jobs you own — you run it as `postgres`, which
           created them, so this is automatic; a different role gets
           "Job N does not exist or you don't own it".
    IF IT FAILS
           - "permission denied for table job": you used the UPDATE form. Use
             the alter_job statement above.
           - "function cron.alter_job(bigint, active => boolean) does not
             exist": pg_cron older than 1.4. Upgrade it (see A2 note (b)).
           - Unsure who owns the jobs: select jobname, username, active from cron.job;
           - Anything other than 8/6, or an unexpected job name: STOP. Do not
             proceed to the dry run. Compare against
             select jobname, schedule, active from cron.job order by jobname;
             expected schedules are listed in docs/OPERATIONS.md section 3.
    PASS (statement + row effect verified offline on PostgreSQL 18.6)

--------------------------------------------------------------------------------
Only the jobs in this section may ever be switched on by hand, and only in
this order. The eight gate jobs are the only ones this checklist enables; the
SQL below is the exact text the test suite reads from this file and executes
against PostgreSQL, so what you run here is what is verified.

G1. Enable writing and publishing, after SECTION E has passed.
    DO     select cron.alter_job(jobid, active => true) from cron.job
            where jobname in ('write-desk','publish-scheduler');
    EXPECT active count goes from 6 to 8; the 6 remaining gate jobs stay
           inactive. After that:
             select jobname, active from cron.job order by jobname;
             -> write-desk true, publish-scheduler true, the other 6 gate jobs
                false, the 6 safe jobs true
           Within an hour: pipeline_runs rows appear every 10/30 minutes, and no
           more than 18 posts land per UTC day. Verify:
             select count(*) from public.posts
              where status='published'
                and published_at >= date_trunc('day', now() at time zone 'utc');
             select function, count(*) filter (where ok) ok_runs, max(started_at),
                    max(error) filter (where not ok)
               from public.pipeline_runs
              where started_at > now() - interval '2 hours' group by function;
    IF IT FAILS  Close the gate again with the statement in B2. Investigate with
           cron.job_run_details + the function logs; fix forward, re-run E2-E5
           before re-enabling.

G2. After 24 hours of G1 behaving, enable the editions and the reader alerts.
    DO     select cron.alter_job(jobid, active => true) from cron.job
            where jobname in ('auto-publish-morning','auto-publish-midday','auto-publish-evening',
                              'breaking-news-monitor','notifications-dispatcher');

--------------------------------------------------------------------------------
  -- 1. Stop everything that can change public content or reader state.
  --    This is the same statement as B2 — one canonical gate, no variants.
  select cron.alter_job(jobid, active => false)
    from cron.job
   where jobname in ('write-desk','publish-scheduler',
                     'auto-publish-morning','auto-publish-midday','auto-publish-evening',
                     'breaking-news-monitor','notifications-dispatcher',
                     'newsroom-maintenance');
  -- 2. Stop everything, ingestion and monitoring included — reversible,
  --    deletes nothing; use when you want total silence, not just safety.
  select cron.alter_job(jobid, active => false) from cron.job;
  -- 3. Back to the post-migration state (6 safe jobs only).
  select cron.alter_job(jobid, active => true) from cron.job;
  select cron.alter_job(jobid, active => false)
    from cron.job
   where jobname in ('write-desk','publish-scheduler','auto-publish-morning',
                     'auto-publish-midday','auto-publish-evening',
                     'breaking-news-monitor','notifications-dispatcher',
                     'newsroom-maintenance');
  -- stop one feed
  update public.content_sources set active = false where name = '<feed>';
  -- un-publish one article without deleting it (see E4 for the exact form)
  -- take one article out of the index entirely (kept in the table)
  update public.posts set status = 'archived', archived_at = now() where slug = '<slug>';
